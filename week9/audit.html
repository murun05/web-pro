Website Accessibility Audit Report

1. Introduction

I used Google Lighthouse in Chrome DevTools to evaluate the accessibility of my Web Pro homework hub (murun05.github.io/web-pro/). I ran the audit with only the Accessibility category selected, once before and once after fixing the problems I found.

2. Before the Fixes

Initial Lighthouse accessibility score: 69/100

The page looked fine visually, but it was well below the 90 I wanted to reach.

3. Issues Identified

One problem was flagged directly by Lighthouse. The other two I found by reading my own HTML.

Issue 1: Links do not have a discernible name (flagged by Lighthouse)

The Week 9 link to audit.html was never closed with </a>. My <ul> and <section> for Week 9 were also left open. A screen reader needs text inside a link to announce it, and an unclosed link can leave empty links in the page.

Issue 2: Two pages pasted into one file (found in the code)

My index.html had two full documents glued together: a second <!DOCTYPE html>, <html>, <head> and <body>, with my old plain homework list underneath the new design.

Issue 3: Broken lists in the old copy (found in the code)

In the old list, some <li> items sat outside any <ul> because of a misplaced </ul>, and the links used the browser's default blue on my dark background, which is hard to read.

4. Accessibility Fixes

Fix 1: Close the link and the list

I gave the link clear text and closed the <a>, <li>, <ul> and <section> tags.

Before (index.html)

<li><a href="week9/audit.html"> website audit

</main>

After (index.html)

<li><a href="week9/audit.html">Website Audit</a></li>
</ul>
</section>
</main>

Fix 2: One document, one structure

I deleted the duplicated old page so the file has a single <html lang="en">, one <head> and one <body>. This also removed the old list with the unreadable blue links.

Before (index.html)

</head><!DOCTYPE html>
<html lang="en">
...
</html>
<body>
  <h1>My Web Pro Homework</h1>

After (index.html)

<!DOCTYPE html>
<html lang="en">
<head> ... </head>
<body> ... </body>
</html>

Fix 3: Valid lists

Every <li> is now inside its own <ul>, one list per week card.

Before (index.html)

<h2>Week 5</h2>
</ul>
  <li><a href="week5/counter.html">Week 5 Task 1</a></li>

After (index.html)

<h2>Week 5</h2>
<ul class="task-grid">
  <li><a href="week5/counter.html">Counter</a></li>
</ul>

Fix 4: Smaller improvements

I hid the decorative icons from screen readers, added a skip link and a visible keyboard focus outline, and darkened the hover color so the white link text stays readable.

Before (index.html)

<svg width="18" height="18" viewBox="0 0 24 24">

After (index.html)

<svg aria-hidden="true" focusable="false" width="18" height="18" viewBox="0 0 24 24">

After the fixes, the report still lists "Identical links have the same purpose" under Best Practices. It is an informational item and does not change the score. It appears because link names such as "Task 1" repeat across different weeks.

6. Which Change Mattered Most

The most important change was closing the Week 9 link and removing the duplicated page. The unclosed link matches the one failing audit Lighthouse showed me. I did not test each fix on its own, so I cannot say exactly how many points each one gave.

A screen reader announces a link by its text. If a link has no text, the user hears only "link" and cannot tell where it goes. Closing the tags properly and keeping a single clean document means the browser builds the page the way I meant it to be built, so every link has a name and every list item sits in a list.

7. Conclusion

I closed the unclosed link and list tags, removed the duplicated old page, made sure all list items are inside lists, and added a few accessibility improvements. These changes raised my Accessibility score from 69 to 100.
